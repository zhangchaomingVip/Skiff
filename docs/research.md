## 〇、一句话定位

**一个统一管理多家 AI coding agent 的桌面壳，核心价值是"每个会话下都能直观看到 token 用量"。**

- 对标 Orca 的"统一接入"，但把 Orca 最弱的"用量可视化"做成招牌。
- Pi 内核好用但无可视化页面 → Skiff 给它套一个好看、透明的壳。
- 先做给自己用；用得好再放出去。

## 三、MVP 定义（v0.1，自用优先）

### 3.1 首次使用故事
1. 装好 Skiff（Tauri）
2. 配好 agent（先接 Pi）
3. 开会话对话
4. **在会话下方实时看到 token 用量拆解**（系统/工具/历史/缓存）

### 3.2 明确不做（v0.1）

- 不做插件市场

### 3.3 验收标准
- 连续一周不切回终端，即视为 v0.1 可用。

## 四、技术架构与数据流（抽象）

### 4.1 核心约束
- 用量数据存在于 Provider 的响应中，而非 Agent 运行时的事件流——这是"token 可视化"的数据源前提。

### 4.2 数据流图
```
UI ──> 后端 ──> Agent 内核 ──> 用量采集层 ──> Provider
 │                        │              │
 └──< 对话流 <────────────┘              └──< usage 回写聚合
```
会话级 token 面板的数据来自"用量采集层"回写的 usage，而非 Agent 事件流。

### 4.3 设计原则（二期细化，先不落地）
- 在应用层拦截 Provider 流量并按会话聚合用量，而非系统级透明代理
- 采集层与 UI 解耦，使多 Agent 接入天然复用同一套用量管道

## 五、差异化防御

### 5.1 竞品为什么没做好
- **Orca**：定位"舰队指挥台"，重全功能，用量是附属信息，不是一等公民 → 不愿意为"可视化细节"投入
- cc-switch：能统计但不能对话
- Pi 套壳：多数无 Windows、无 token 细节

### 5.2 真正难抄的东西
- **把"每会话 token 可视化"做成肌肉记忆级的顺手体验**，而不是堆功能

## 七、命名与商标风险

- **调研结论（2026-10-02）**：Notion 于 2024-02 收购 Skiff（加密邮件/协作），
  随后关停其邮件服务、推出基于 Gmail 的 Notion Mail；据 2026 年多家媒体报道
  （Ars Technica / 搜狐 / 腾讯云等），Notion 已于 2025-09-22 关闭 Notion Mail，
  Skiff 品牌实质**已退出市场**。→ 命名冲突风险**低**。
- 仍需做：花 5 分钟查 GitHub `zhangchaomingVip/Skiff`、npm `skiff-agent` 是否被他人占用（功能同名 ≠ 商标，但占位安全）。
- 结论建议：可保留 Skiff；若求稳可加后缀（如 `skiff-shell`）。
