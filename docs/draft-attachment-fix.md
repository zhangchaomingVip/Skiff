# 草稿附件保存修复

实施日期：2026-10-30。背景与竞品规则见[修复前调研](draft-attachment-persistence-research.md)。

## 修复后的行为

允许导入的图片和文本不再因为 base64 / JSON 膨胀而提前触发草稿限制。单张 5 MiB 图片、512 KiB 文本，以及 4 张最大图片加 4 份最大文本（共 22 MiB），均可保存并刷新恢复。

容量按图片解码后的字节、文本 UTF-8 字节计量。导入上限与保存上限复用 `src/chat/attachmentLimits.ts`。当前草稿与编辑前备份各有 32 MiB 附件预算，全局附件正文预算为 256 MiB；这些是应用预算，不代表数据库实际磁盘占用或 WebView2 配额。相同附件 ID、类型和内容在当前草稿及备份中共享实体，只计一次全局占用。空间不足时优先保留已保存内容，不静默淘汰其他聊天的未发送草稿。

缺失附件只阻止发送，不再禁用添加入口。每项提供“重新添加”和“移除”；重新添加明确替换该项，允许文件改名。发送按钮与 Enter 均有缺失检查。真正的保存失败会指出附件名称，区分应用预算、存储配额和其他异常，并提供“重试保存”。当前内存内容仍可使用。

## 存储与迁移

`src/chat/draftStorage.ts` 将 `skiff-drafts` 升级到版本 2：

| 对象仓库 | 内容 |
| --- | --- |
| `drafts` | 草稿文字、编辑上下文、附件元数据与 `contentId` 引用 |
| `attachments` | 独立 Blob，按聊天索引 |
| `sizes` | 各聊天已保存附件的内容字节数 |

正文、引用、计量与无引用实体清理在同一事务内提交。打字保存只读取轻量计量和附件键，不读取全部附件正文，不重写未变附件。当前草稿移除附件后，若编辑前备份仍持有引用，实体继续保留；最后一个引用释放后清理。

旧版内联正文在成功迁移前保留。迁移事务失败及后续编辑重试失败时，不以仅元数据版本覆盖唯一正文。未知写入异常回滚，保留上次已提交记录及对应内容 ID；只有确认的 `QuotaExceededError` 才尝试保留已有实体、为新附件保存缺失标记。正常保存保留修订屏障、删除屏障和退出时立即启动事务的机制。

## 边界

旧版本已经丢失的附件正文无法从元数据恢复，需要重新添加一次。DOCX 仍只保存提取后的正文，不保存原始文档和内嵌图片。启动恢复仍会加载所有有效聊天草稿正文；按聊天延迟加载、存储管理面板和原生文件存储不在本次实现内。保存成功依赖本机存储可用；退出时尽力提交不等于保证强制结束进程或磁盘故障时仍能完成写入。
