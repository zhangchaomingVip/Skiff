# 草稿附件持久化调研与优化建议

调研日期：2026-10-30。范围：修复前实现、ChatGPT / Claude / Gemini 的公开规则、存储方案和验收建议。本文保留修复前的排查记录；后续已实施的变更与验证见[草稿附件修复记录](draft-attachment-fix.md)，下文的旧代码位置及未实施说明属于调研时状态。

## 结论

当前提示符合 019 功能原先规定的降级行为，但原有容量策略与附件导入能力存在明显冲突：一张允许添加的 1 MiB 图片，已经无法完整保存进草稿。建议把“成功导入且保存完成的附件，重载后能够恢复”作为正常路径，把仅内存可用作为异常状态。

优先修复恢复入口和错误分类，再拆分草稿元数据与附件内容存储。仅修改三个容量常量不能同时解决可靠性、性能与恢复体验。

## 1. 当前实现的事实与影响

| 位置 | 当前行为 | 影响 |
| --- | --- | --- |
| `src/chat/drafts.ts:13–29` | 附件正文按 `UTF8(JSON.stringify(body))` 计量；1 / 4 / 20 MiB 限制；超额保存元数据和 `needsReattach` | 这些是应用预算，不是 IndexedDB 固定配额，也不是模型输入上限 |
| `src/chat/images.ts:3–18` | 最多 4 张图片，每张原始文件 5 MiB；转为 base64 字符串 | base64 约膨胀 1/3，实际可恢复图片原始大小上限只有 786,429 字节 |
| `src/chat/textAttachments.ts:5–21` | 最多 4 个文本 / Word 文件；普通文本每个 512 KiB，UTF-8 解码 | JSON 转义增加保存计量，极端但合法的文本也可能超出 1 MiB |
| `src/chat/wordAttachments.ts:2–26` | DOCX 原文件最多 10 MiB，提取正文最多 512 KiB | 草稿保存的是提取正文；原始 DOCX 和内嵌图片不在当前恢复承诺内 |
| `src/chat/drafts.ts:27–30` | 编辑提问时，当前附件与 `edit.previous` 附件共同计入预算 | 用户看不见的先前草稿也可能触发提示；同一内容可能重复存储、重复计费 |
| `src/chat/drafts.ts:136–151` | 每次持久化先 `getAll()` 读取全部草稿正文；任何写入失败都尝试只存元数据 | 调大上限后，每次防抖保存会放大全库读取、字符串编码和结构化克隆开销；非配额故障也可能显示容量提示 |
| `src/chat/useDraft.ts:47` | 多种失败统一显示“超出保存容量或存储配额” | 无法知道哪些附件没存、是应用预算还是存储故障，也没有相应解决入口 |
| `src/components/ChatView.tsx:179–182`、`Composer.tsx` | 缺失附件会给 Composer 传入 `disabled`，添加、发送等按钮被禁用，但文字输入框仍可编辑；占位行只有“移除” | 常规“+”按钮无法直接重加附件。拖放处理没有同样的禁用检查，是旁路，不应成为恢复依赖 |
| `src/chat/useDraft.ts:37–40` | 按附件种类和同名文件消除缺失占位 | 同名不等于同一内容；建议明确替换目标，并记录内容摘要 |

补充边界：

- 20 MiB 只累计附件正文，不包括输入框文字、文件名等元数据，不能称为整个草稿库的磁盘上限。
- “元数据保存成功”不等于“完整附件保存成功”。完整内容仍保留在运行期内存中，所以当前可以发送。
- 现有版本屏障和删除标记、防止迟到保存复活、失败发送保留、发送被接受后只清除已提交内容等设计应保留。
- `beforeunload` / `pagehide` 已尽力立即启动事务，但不能保证进程崩溃或系统强制结束时完成保存。
- 恢复按钮问题已在独立 headless Edge 上使用真实 React 组件和模拟桥复现，见 1.2；未进行真实 Tauri / pi 全链路验证。

### 1.1 调用真实 `prepareDraft` 的边界实验

使用 Node 和仓库现有 TypeScript loader，在独立进程中直接构造附件并调用纯函数。未读写实际 IndexedDB、工作区索引、会话或模型配置；图片采用合成字节，仅验证容量判断。

| 输入 | 原始大小 | 保存计量 | 正文是否保留 |
| --- | ---: | ---: | --- |
| 图片 | 512 KiB | 699,054 B | 是 |
| 图片 | 786,429 B | 1,048,574 B | 是 |
| 图片 | 768 KiB = 786,432 B | 1,048,578 B | 否 |
| 图片 | 1 MiB | 1,398,106 B | 否 |
| 图片 | 5 MiB | 6,990,510 B | 否 |
| 纯 ASCII 文本 | 512 KiB | 524,290 B | 是 |
| 全换行文本 | 512 KiB | 1,048,578 B | 否 |

图片计量为 `4 * ceil(rawBytes / 3) + 2`，其中 2 是 JSON 字符串引号。因此 768 KiB 已越界，不只是“超过 1 MiB 的图片”才有问题。全换行文本是边界样例，不能据此推断普通文档普遍无法保存。

### 1.2 浏览器复核：恢复入口及测试盲点

使用独立、临时的 headless Edge 浏览器上下文，在 1421 端口的 `tests/retrievability.html` 中运行完整 React 界面与模拟桥。通过真实“+”按钮打开文件选择器，添加合法的 512 KiB UTF-8 文本（反斜杠重复构成，JSON 转义后超过保存上限），等待降级提示，再进入保留存储的恢复页面。

| 状态 | “+”添加按钮 | 发送按钮 | 文字输入 |
| --- | --- | --- | --- |
| 刷新前、附件仅内存可用 | 可用 | 可用 | 可编辑 |
| 刷新后、附件正文缺失 | 禁用 | 禁用 | 可编辑 |
| 测试直接给隐藏 input 设置同名替换文件后 | 可用 | 可用 | 可编辑 |

以下为调研日实际打开的官方页面内容。官方 MB / GB 保留原单位，不擅自换成 MiB / GiB；Skiff 当前代码采用二进制单位。规则受套餐、客户端和产品更新影响。

| 产品与范围 | 单文件限制 | 数量 / 内容限制 | 可以借鉴的产品规则 |
| --- | --- | --- | --- |

| ChatGPT Library [2] | 沿用文件类型限制 | 已上传和创建的文件自动保存，可重新添加到聊天；临时聊天等有例外；可查看存储占用 | 文件与聊天具有独立生命周期，可复用已保存文件；不能把已保存文件的规则等同于未发送草稿恢复 |

| Gemini Apps [4] | 非视频支持文件 100 MB；视频 2 GB | 同一提示最多 10 文件，受可用性影响；另有音视频时长、上传频率和上下文限制 | 明确区分存储不足、滚动用量超限、内容过大的不同提示和处理方法 |

**没有核实的部分：**本次查阅页面没有给出这些产品“未发送附件的本地草稿容量”“刷新一定恢复”“跨设备草稿同步”的完整保证，也没有披露对应客户端的 IndexedDB / 文件存储实现。不应据此宣称 ChatGPT 的附件草稿无限制或永不丢失。

ChatGPT 的公开文件管理规则足以支持“文件实体与聊天引用分离”的产品参考，但不能证明它内部采用某种数据库或具体提交顺序。

### 2.1 不应照搬的容量数字

- 512 MB 文件上传能力通常伴随工具读取、文本提取或检索能力；不等于能够把全部内容直接塞入模型提示词。
- Skiff 的 `appendTextFiles()` 当前把正文完整追加到提示词。即使扩大本地存储，也需要独立检查当前模型、协议和中转服务可接受的请求与上下文大小。
- ChatGPT 上传 FAQ [1] 给出共享上传存储 25 GB / 用户、100 GB / 组织；Library 页面 [2] 另按套餐列出 Free 500 MB、Go 4 GB、Plus / Business 20 GB、Pro 100 GB。两页的口径不能简单视为同一上限，本次没有核实其完整对应关系，不以这些总量为 Skiff 定标。

## 3. 建议的产品规则

### 3.1 把“可发送”和“已保存”分开

| 状态 | 用户可见信息 | 操作规则 |
| --- | --- | --- |
| 读取 / 处理中 | 文件卡片显示“正在读取” | 尚未就绪的附件不能发送 |
| 内容就绪，正在保存 | 显示“正在保存” | 可以按当前发送策略使用；不能显示已保存 |
| 保存提交成功 | 显示“已保存到本机” | 正常情况下重启可恢复；该状态不表示云同步 |
| 仅内存可用 | 点明文件名、失败原因和“刷新或关闭后需重新添加” | 有内容时仍可发送；提供重试，避免统一阻断 |
| 重载后内容缺失 | 文件卡片显示“需要重新添加” | 只阻止包含缺失附件的发送；保留文字编辑、添加、替换与移除能力 |

优先采用附近的轻量保存状态，故障持续时才显示醒目提示。无需在每次输入后弹通知，也不应默认增加每次关闭的确认弹窗。

建议文案示例：

- 应用预算不足：“图片「截图.png」未保存到本机：草稿附件空间不足。当前仍可发送，刷新或关闭后需重新添加。”操作：`管理草稿空间`、`重试保存`。
- 存储写入失败：“附件未能保存到本机。当前仍可发送，刷新或关闭后需重新添加。”操作：`重试`、`查看原因`。
- 恢复缺失：“「截图.png」需要重新添加后才能发送。”操作：`重新添加`、`移除`。
- 草稿文字也未保存时，应明确写“本次输入未能保存”，不能只说附件问题。

细分内部原因：`attachment_limit`、`draft_limit`、`app_budget`、`storage_quota`、`storage_unavailable`、`transaction_failed`、`content_missing`。文件卡片记录各自结果，不再只保留聊天级 `limited` 布尔结论。`storage_quota` 应有 `QuotaExceededError` 等证据，未知写入错误不能归因为配额。

### 3.2 容量建议：以当前功能为边界

以下是建议初值，供实施和实测调整，非竞品标准，也非浏览器保证值。**前提是正文独立存储，按二进制 / UTF-8 内容字节计量，不再按 JSON 中的 base64 字符串计量。**

| 项目 | 建议初值 / 规则 | 理由 |
| --- | --- | --- |
| 导入限制 | 暂维持图片 5 MiB × 4；文本 / 提取正文 512 KiB × 4 | 先解决持久化不一致；扩大文件能力需要另外评估上下文、解析及请求限制 |
| 单个普通草稿附件预算 | 32 MiB | 现有最大就绪内容约为 20 MiB 图片 + 2 MiB 正文，留有余量 |
| 编辑时保留的先前草稿 | 独立保留同等容量；当前与先前合计可达 64 MiB | 取消编辑不能因共享低预算而丢掉原草稿；相同内容去重 |
| 全部未发送附件 | 默认应用预算 256 MiB，可在设置中调整 | 比当前 20 MiB 更适合多聊天使用；预算不等于预先分配内存或浏览器配额 |
| 空间提示 | 到预算约 80% 时提示，可查看各聊天占用 | 在实际失败之前提供处理入口，不需要每次打扰 |
| 超预算 | 保住已有完整草稿，说明新增内容未保存，允许管理空间或调整预算 | 未发送内容不是可随意淘汰的普通缓存 |

“默认可恢复”的承诺仍以保存事务 / 原生提交成功为准；磁盘不足或存储不可用时必须如实降级。内容预算之外还需预留元数据、数据库开销、迁移和临时写入空间，不能只看 `used + contentBytes <= budget` 就假报成功。

如果短期只调常量，至少应覆盖当前合法附件组合、base64 / JSON 转义和先前草稿。临时的 8 / 96 / 256 MiB（单附件 / 含先前内容的单草稿 / 全局附件序列化计量）可以作为边界验证候选，但**不建议单独上线**：每次保存的 `getAll()` 和全库重新编码必须先处理；它也不能解决实际存储不足。正式规则应由导入能力推导并有回归约束，避免再维护一组相互冲突的常量。

## 4. 存储实现建议与取舍

### 4.1 首选的近期改造：IndexedDB 元数据与 Blob 分离

在现有 IndexedDB 路径上改造，变更范围小于立即引入原生存储：

- `drafts`：仅保存文字、附件引用、编辑上下文、修订号及状态所需元数据。
- `attachments`：按受控 ID 或内容摘要保存 Blob、媒体类型、内容字节数；同一内容尽量只保存一次。
- 新附件只写入一次正文；打字只更新草稿记录，不再全库读取附件正文。
- 存储占用从元数据读取；同库事务保证附件、草稿引用和统计一致。多窗口写入仍应在事务内重新核算，不能只靠前端 Map 保证全局预算。
- 启动先加载草稿目录，需要时再加载当前聊天附件；不再把所有聊天附件一次性 `getAll()` 到内存。
- base64 仅在现有 pi 传输需要时生成。显示预览可用对象 URL，并在不再使用时释放；不要为去重或预览长期保留多份等价字符串。

IndexedDB 的配额由浏览器存储管理决定，20 MiB 不是通用上限。`navigator.storage.estimate()` 可提供诊断估计，`persist()` 可在支持的环境请求持久存储，但都不能承诺写入必成功，且 WebView2 中支持情况需要实际验证。[5]

### 4.2 原生文件存储：适合桌面长期可靠性需求

若 Skiff 需要让草稿独立于 WebView profile、便于诊断和备份，可把附件实体放在 Tauri 应用数据目录，草稿只存引用。这能绕开浏览器附件配额和 base64 持久化开销，但不是零成本升级：

- 写入须采用可靠提交顺序：内容先落盘，再提交引用；处理临时文件、崩溃恢复、Windows 替换文件行为，以及修订号和删除屏障。
- 应使用不受文件名控制的存储 ID；原生命令只允许访问受控目录，并校验路径及能力权限。原文件移动或删除不应导致已复制的附件失效。
- 草稿目录与 workspace 的聊天索引必须能协调恢复；只迁移附件文件、不解决索引引用，仍可能出现“文件存在但聊天找不到”。
- 文件存储仍可能受磁盘不足、权限和用户清理影响；本机数据落盘不等于加密保存，也不等于云同步。

不建议为这次问题直接更换模型消息协议或修改 pi 会话文件。可先保留传输形态，只替换草稿持久化层。原生方案作为后续有明确可靠性目标时的选择。

### 4.3 清理和迁移

- 优先清理无引用实体、过期临时文件和已有恢复副本的缓存；未发送草稿不采用静默 LRU / TTL 删除。
- 当前草稿、`edit.previous`、发送中的快照和其他聊天都可能持有引用；只有引用全部解除后才能回收实体。
- 发送失败保留；发送被接受后，只释放已提交内容对应的草稿引用，确保异步发送期间新输入仍在；历史附件由其自身生命周期决定。
- 已有 v1 正文逐条迁移：先写入新实体、验证可读取，再切换引用；遇到旧版 `needsReattach` 不能假装修复。保留必要回滚 / 恢复路径，避免重复计算容量或因中途退出丢掉唯一副本。
- 空间释放、用户手动重试或预算调整后，可重试仍在内存中的未保存附件；不要用无限自动重试掩盖持久故障。

## 5. 实施顺序

1. **恢复入口与可观测性**：缺失附件只拦发送，不禁用添加 / 编辑；提供目标明确的重新添加；记录每附件结果和具体失败原因；同名替换不再视为身份验证。
2. **正文独立存储与一致预算**：Blob 分离、去重、按需加载、避免每次打字读写全库正文；再应用容量初值，显示占用和管理入口。
3. **可靠迁移与生命周期收口**：先前草稿、发送快照、多窗口、删除屏障、孤立实体和空间释放后重试；视需要评估原生文件存储。

建议本次产品目标先定为“现有支持范围内的附件，在保存成功后能重启恢复”，暂不承诺对齐 ChatGPT 的大文件分析能力。

## 6. 后续实施的验收建议

- 边界：768 KiB / 1 MiB / 5 MiB 图片，以及 4 张最大图片 + 4 份最大正文；正常草稿、编辑和取消编辑均可保存恢复。
- 失败：应用预算超限、真正 `QuotaExceededError`、非配额事务异常、正文与元数据都失败，应显示不同结果和可执行操作。
- 恢复：刷新后缺失附件仍能直接点击“重新添加”；可以编辑文字、添加其他附件或移除占位；缺失内容不得当作空文件发出。
- 性能：全局附件占用较高时，连续打字不读取全部正文、不重新写入未变更附件；测量写入耗时、启动耗时和内存峰值，再确定预算。
- 一致性：两个窗口并发保存、编辑取消、发送期间继续输入、失败发送、归档 / 删除、迁移中断、退出中断均不丢内容或复活已删除草稿。
- 降级：存储不可用时当前内存附件仍可发送；恢复存储或释放空间后可手动重试；不把“仅保存文字”显示为整体已保存。
- UI 实施需验证浅色 / 深色与键盘操作。若改动发送链、RPC 或原生命令，按仓库要求运行隔离的完整 CDP 验证，不接触真实 agent 目录或破坏 workspace localStorage。
