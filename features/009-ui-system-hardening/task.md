# 009 · 前端视觉系统收敛与页面体验优化

## 背景

Skiff 已经具备模型优先入口、聊天、提供商管理、明暗主题、响应式布局和 Voyage 航行台等完整产品能力，也在 `src/tokens.css` 中定义了颜色、间距、圆角、字体、阴影与动效 token。

当前问题不是“没有设计”，而是设计规则尚未完全工程化：页面主要依赖 `src/index.css` 中的全局选择器和页面级 class，部分 token 未定义、同一选择器在文件后部被再次覆盖、控件尺寸和图标来源不统一，浅色主题中的小号辅助文字对比度不足。随着功能持续增加，这些细小偏差已经累积为明显的视觉层级、可读性和一致性问题。

本任务参考成熟桌面工具在语义 token、组件原语、信息层级、状态反馈和视觉回归方面的做法，但不复制其他产品的品牌外观。Skiff 应保留现有蓝色品牌、模型优先入口和 Voyage 航行隐喻，目标是让这些特征更清晰、更稳定，而不是把界面改成另一款产品。

已确认的基线问题包括：

- 浅色主题三级文字 `#999` 对 `#fafafa` 的对比度约为 2.73:1，大量 11px / 12px 辅助信息阅读困难。
- `src/index.css` 引用了未定义的 `--space-15` 和 `--radius-xs`，相关声明会被浏览器丢弃。
- `.msg`、`.composer-context`、`.model-picker` 等核心选择器存在重复定义或断点规则互相覆盖。
- 主按钮主要使用中性黑白，品牌强调色更多停留在 focus 和边框，页面缺少稳定的主视觉焦点。
- 图标同时来自自绘 SVG、品牌 SVG 和 Unicode 字符，线宽、基线与光学尺寸不一致。
- 主题只在 React effect 后写入 DOM，未配置时固定使用暗色，存在主题闪烁且不能真正跟随系统。
- Launcher 模型卡中的模型、线路、能力、上下文、价格和操作接近等权展示；008 要求的扣费账户信息在当前卡片中尚未完整呈现，优化时必须补齐，不能作为可删除的噪声。

## 目标

1. 建立可执行的 Skiff 视觉系统，使颜色、字体、间距、圆角、控件尺寸、状态和动效都有唯一来源。
2. 在不改变聊天协议、模型选择、线路授权、费用计算和会话语义的前提下，提高 Launcher、聊天页、设置弹窗和 Voyage 面板的一致性与完成度。
3. 强化浅色和深色主题的可读性，普通文本对比度达到 WCAG AA；状态不能只依赖颜色表达。
4. 建立少量稳定的组件原语，阻止新页面继续直接复制 `.btn`、`.icon-btn`、卡片和字段样式。
5. 明确页面中的主操作、当前选择、状态和辅助信息，使用户能快速扫描，而不是阅读等权的工程数据。
6. 支持 `system / light / dark` 三态并避免首次绘制闪烁。
7. 为主题、关键页面和主要窗口宽度建立可重复的视觉验收基线。

## 非目标

- 不重写 pi RPC、Tauri 命令、模型发现、Provider 配置格式、线路选择或授权状态机。
- 不改变 Offer、RouteSnapshot、费用和 token 的业务语义。
- 不为了视觉优化引入第二套页面或复制第二套模型选择逻辑。
- 不追求移动端网站式布局；Skiff 仍是桌面应用，但必须在项目支持的最小窗口下可用。
- 不照搬 cc-switch 的橙色品牌、应用导航或供应商页面结构。
- 不以一次性大规模重写 `index.css` 为目标；每一阶段都必须可独立验证和回滚。
- 不强制引入 Tailwind、Radix 或某个图标库。若新增依赖，必须说明它解决的具体问题、体积影响和迁移边界。

## 设计与实现原则

- **语义优先**：组件只消费 `surface / foreground / action / selected / success / warning / danger` 等角色，不直接依赖任意颜色值。
- **层级优先于装饰**：先解决标题、正文、辅助信息、状态和动作的权重，再增加阴影或动效。
- **一个视图一个主操作**：品牌强调色只突出当前页面最重要的可执行动作。
- **桌面高密度但可读**：不要按截图像素机械放大；统一紧凑、常规和主操作三档尺寸。
- **品牌连续性**：保留 Skiff 蓝色、品牌标记与 Voyage 语言；品牌色不承担错误、警告等语义。
- **渐进迁移**：先建立 token 和原语，再逐页替换；禁止新旧规则在同一组件内长期混用。
- **无障碍默认开启**：键盘焦点、reduced motion、文本对比度、可读标签和非颜色状态表达都属于完成标准。

## 执行顺序与交付依据

执行依赖为：阶段 0 固定复现环境 → 阶段 1 冻结目标设计与 CSS 组织 → 阶段 2 验证组件原语 → 阶段 3 完成主题 → 阶段 4–6 逐页迁移 → 阶段 7 查漏 → 阶段 8 最终回归。阶段 1 和 2 的产物完成前，不进入页面批量迁移。

实施期间需在本目录建立以下产物；它们是待完成的任务，不代表本规划已完成实现或验收：

## 模型选择与计费展示契约

本节细化 008 的展示要求，并保留 007 的线路、授权和历史快照语义。允许降低辅助信息的视觉权重，但不能降低用户在选择前识别线路、价格和扣费主体的能力。

| 信息 | 默认卡片与确认前的要求 |
| --- | --- |
| 模型与线路 | 显示模型名/ID、默认线路/供应商、有效线路数量；多线路明确提示需要选择，不能将默认线路当作已经确认的目标 |
| 价格 | 默认卡片显示默认 Offer 的输入、输出两项单价，明确币种及“每百万 token”；不得合并为一个无单位数字、用状态替代价格或将未知显示为免费 |
| 扣费账户 | 默认卡片以可读文字展示默认 Offer 的账户；未配置显示“未标注”，不推断账户相同，不展示密钥 |
| 能力与上下文 | 保留 008 要求的简短能力和上下文摘要，可放在较低权重的第二行；解释文字、长模型 ID 的完整内容、非默认线路详情可通过可聚焦的详情入口展开 |
| 多线路确认 | 每条可选 Offer 在确认前可读出自身的模型、线路、账户、输入/输出单价、币种和单位，不能只沿用卡片中默认 Offer 的信息 |

单线路保持直接开始聊天的流程，因此必要计费字段必须在卡片中默认可见，不增加确认弹窗，也不能只放进 hover Tooltip。多线路继续先选择具体 Offer。窄窗口允许信息换行和区域滚动，不能隐藏必需字段；更改呈现方式不改变选中 Offer、跨账户授权或历史价格来源。

## 必须验证的交互契约

| 对象 | 迁移验收 |
| --- | --- |
| Dialog | 进入时聚焦合理目标；添加项目聚焦路径，删除确认聚焦取消；Tab/Shift+Tab 留在模态内，背景不可操作；关闭后回到触发器，触发器已消失时回到合理的稳定位置 |
| 关闭与提交 | 普通 Escape 关闭当前最上层弹层；添加项目 pending 时保留禁止 Escape、关闭和取消的规则；逐个记录现有遮罩点击策略，通用 Dialog 不得默认将所有表单改成点击外部即丢弃草稿 |
| 选择器与 Tooltip | 线路选择保留搜索、上下方向键、Enter 和 Escape；焦点移动不等于提交选择；Popover 按原有策略处理外部点击与焦点返回；Tooltip 可由键盘访问且不包含唯一的必需信息 |
| Button / Field | 非提交按钮默认 `type="button"`，表单显式提交；label、错误关联、受控值及 ref 能透传；disabled/loading 从行为上阻止重复操作；Enter 不造成按钮与 form 双重提交 |
| Composer | 保留 Enter 发送、Shift+Enter 换行、输入法组合输入不发送；命令/文件建议菜单打开时键盘优先级保持一致；附件、停止、草稿和模型选择行为不因样式包装改变 |
| 业务回归 | 单线路/多线路进入聊天、当前会话切换模型、跨账户授权、历史恢复及价格快照按 007/008 执行；针对迁移组件验证一次真实 UI 事件链，而非仅运行 reducer 测试 |

每个迁移阶段记录执行步骤、期望和实际结果。静态截图用于视觉核对，交互需通过浏览器实际操作或适当的行为测试验证，不能以组件预览替代。发现既有行为不满足上述目标时记录为显式修复项，不将其描述为已通过基线。

## 可重复的视觉验收环境

- 使用独立本地端口上的 `tests/preview.html` 和模拟 bridge；预览存储与日常运行隔离，使用固定的虚构项目、模型、线路和账户。浏览器中直接打开生产入口产生的 Tauri bridge 错误不作为正常页面基线。
- 采集基线前修正预览页的主题入口：移除查找旧深色媒体查询并复制 CSS 变量的覆盖逻辑，在挂载前通过与应用一致的主题存储和 `data-theme` 初始化；阶段 3 同步适配新主题入口。预览不得维护第二套颜色表。
- 为正常 Launcher、单/多线路、未知账户、无模型、加载/错误、长聊天与工具结果、设置弹窗、模型选择器、Voyage 展开/折叠建立命名 fixture。固定 ID、排序、价格、计数、当前时间、相对时间、用量及仪表值，记录进入目标页面的操作步骤。
- 固定 Windows 环境和浏览器版本，记录字体实际回退、系统缩放与 devicePixelRatio，浏览器缩放为 100%。同一前后对比必须采用相同环境；浏览器与 WebView2 截图分别记录，不跨渲染环境作像素判定。
- 视口以 CSS 像素定义为 `600×400`、`900×700`、`1200×800`，指完整页面视口而非扣除侧栏后的内容宽度。Tauri 另在配置的最小逻辑窗口 `600×400` 验证，并记录实际内区视口和缩放。
- 标准截图矩阵为 5 个场景（正常 Launcher、聊天与工具结果、提供商设置、模型选择器、聊天且 Voyage 展开）× 浅/深主题 × 3 个视口。窄窗口自动折叠航行台时，额外执行展开并验证替代布局。其余 fixture 在 `900×700` 双主题验证；长文本、错误和长表单同时补测 `600×400`。
- 静态对比固定滚动位置和焦点，等待字体与布局稳定，冻结流式、仪表和动画到规定帧；不以冻结模式验证真实交互。主题冷启动、动效和 reduced-motion 单独走查并记录，避免截图工具掩盖闪烁。
- 截图名称采用 `<scene>-<state>-<theme>-<width>x<height>.png`，存入本目录对应的 before/target/after 子目录，环境和复现命令记入 `baseline.md`。对照目标样例检查差异，预期设计变化须写入 `verification.md`，不追求优化前后像素完全一致。
