# 016 · 会话上下文统计口径与超限误报修复

状态：已实施，自动化验证通过。创建日期：2026-10-12。依赖 `014-voyage-panel-polish` 的航行台实现。

本 feature 替代 014 中“上下文按本轮所有请求输入累计”和“上下文读数只能增长”的统计约定；其余工具日志、计时及速度规则继续沿用。调查证据见 [上下文占用误报诊断](../../docs/context-usage-diagnosis.md)。

## 背景与目标

Agent 一轮可能发起多次模型请求，每次重发大量相同上下文。当前 `advanceVoyageContext()` 将本轮每个 assistant 请求的 `input + cacheRead + cacheWrite` 相加，并用于上下文占比和超限提醒，导致累计消耗被误认为单次上下文。

本地历史已精确复现截图：最后一轮 7 次请求累计输入 218,805、输出 1,871，界面显示 `218.81k / 128k` 并警告 `170.9%`；实际上最后一次请求输入为 32,401，pi 包含该次输出的上下文估算为 32,679，仅占 128,000 窗口的 25.53%。同一会话更早的一轮有 19 次请求，不是截图数值的来源。

本 feature 将上下文占用、累计消耗和最近请求输入分开，使实时会话、历史恢复、压缩和回退均使用正确口径，避免工具请求次数增长触发虚假超限警告。

## 统计口径

Skiff 使用 pi 归一化后的 usage，不直接解释供应商原始 `input_tokens`。本机 pi 的 OpenAI 兼容适配器已从 input 中扣除缓存量；Anthropic 的 input 与缓存字段分列。

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| 单次完整输入 | `input + cacheRead + cacheWrite` | 最近请求输入、请求级诊断 |
| 本轮累计输入 | 本轮各请求完整输入之和 | 消耗统计，显示“累计输入 tokens（含缓存）” |
| 本轮输出 | 本轮各请求 output 之和 | 输出消耗与现有平均速度统计 |
| 当前上下文 | 优先使用 pi `contextUsage.tokens` | 窗口占比、进度和提醒 |
| 累计未缓存输入 | 各请求 input 之和 | 未缓存消耗，不代表去重后的内容量 |

缓存命中仍占用上下文。reasoning 是 output 的子集，不额外加入输出或上下文。累计消耗可以超过上下文窗口，不因此触发提醒。`summarizeUsage()` 和费用计算继续按请求累计。

## 数据源与状态约定

### 1. 优先采用 pi 上下文读数

通过现有通用 RPC 桥请求 `get_session_stats`，读取：

```ts
contextUsage?: {
	tokens: number | null;
	contextWindow: number;
	percent: number | null;
}
```

本机 pi 1.1.0 的实现基于当前分支投影，使用最近一次有效 assistant usage，并估算之后新增的消息；压缩后没有新 usage 时可返回 null。其 tokens 包含最近回复的输出，不等同于最近请求输入。pi 的读数本身可能含估算，不能仅凭数据来自 pi 就宣称精确。

在 `SessionState` 保存独立上下文读数，至少区分来源、有效值、未知状态和所属上下文版本。建议来源为 `pi`、`last-request`、`local-estimate`、`unknown`；“是否估算”独立表达。`useVoyageMetrics()` 不再让上下文与本轮累计输入共用一个 input 字段。

tokens 必须是有限非负数，contextWindow 必须是有限正数。占比由同一快照的 tokens/contextWindow 计算；窗口未知时不显示百分比或超限提醒。

### 2. 刷新与并发

- 历史恢复、切换会话、回退/分叉、切换模型后刷新上下文。
- message_end、工具结果、agent_end、压缩完成后合并刷新；流式阶段不为每个 token 发 RPC。
- 同时只保留有限的在途刷新；事件集中到达时合并为后续一次刷新。
- 沿用 session owner/generation 校验，并增加同会话内的刷新序号或上下文版本校验，阻止迟到响应覆盖新状态。
- 切换模型、分支和压缩时失效旧快照。不要把旧 timeline 的 limit 与新 tokens 拼接。
- 短暂 RPC 失败不应中断聊天；同版本旧读数可保留但标明尚未更新。失效前版本的读数不得重新参与提醒。

### 3. 兼容降级

- RPC 不支持或 contextUsage 字段缺失时，允许使用本地兼容路径。
- pi 明确返回 `tokens: null` 时显示待更新；不得用压缩前 usage 回填。不能将字段缺失、明确 null 和数值 0 合并处理。
- 降级路径按消息顺序寻找最近一次有效请求，不能跨请求求和，也不能用本轮单次最大值代替当前值。
- “最近请求输入”为该次完整输入；若用于“当前上下文估算”，则加该次 output，再估算之后尚未进入请求的用户、工具及流式新增内容，并明确标记估算。
- 后续请求已包含的历史内容不能再次加入。`parseMessages()` 将 toolResult 合并进 assistant.blocks，增量估算必须处理这一结构，不能漏计最新工具结果。
- pending 全零占位、无效数值以及无可靠 usage 的 error/aborted 消息不能清零上一条有效读数。没有有效基线时显示未知或粗估。
- 无 usage 的本地粗估须考虑整个可见会话，而非只估算最后一轮；系统提示、工具 schema、图片和压缩投影不可获得时明确其局限。无法可靠区分压缩前后数据时显示未知。

### 4. 读数允许下降

移除对上下文的全航行 `Math.max(previous.context, observed)` 锁定。压缩、回退、新请求以及真实 usage 校正本地估算后，允许显示更小读数。

同请求重复事件应保持幂等，完成后的 usage 优先于迟到的流式占位。防抖依赖请求身份、终态和事件版本，不依赖永久最大值。历史恢复和实时结束必须得到相同统计结果。

## 展示与提醒

- 收起状态栏与展开航行台共用同一上下文读数及窗口。
- 本次航行记录将输入标签改为“累计输入 tokens（含缓存）”，与上下文分开。
- 上下文未知显示 `—` 或“待更新”，不显示伪造的 0% 或剩余额度。
- 使用估算时显示估算标记；说明当前读数包括哪些内容，不保留“同次航行保留最大值”的旧提示。
- 上下文提醒沿用 90% 起的阈值，仅由有效上下文读数触发；估算超窗使用“估算上下文超过窗口”等措辞。
- API 实际 `context_length_exceeded` 继续作为错误展示，不能由累计消耗推断。已完成请求成功，也不保证加入下一条消息后仍低于窗口。

本例预期：上下文约 `32.68k / 128k`、25.5%，无超限提醒；累计输入为 218.81k，回复总消耗仍为 220.68k。
