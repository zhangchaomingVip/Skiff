# 040 · 2K / 4K 尺寸配置入口

状态：实现和隔离验证完成。日期：2026-11-12。

## 问题与结果

图片工作区根据服务中每个模型的 `sizes` 配置分组，没有自动探测供应商能力。默认列表只预填较小尺寸，因此 2K 被禁用，4K 甚至不显示；这并不是实际模型不支持高分辨率的结论。

现在始终显示 1K / 2K / 4K。有配置时选择对应尺寸，并尽量保留当前比例；未配置的档位显示「待配置」，在已有服务时可以点击进入图片生成设置。编辑对应服务/模型后，使用「添加 2K 尺寸」「添加 4K 尺寸」，按服务商实际范围删减并保存，再回到创作页选择。

没有配置任何模型时，档位保持不可选，沿用配置服务引导。不自动修改用户的配置或把任意模型认定为支持 4K，也不因点击配置/添加预设发出模型请求。

## 实现

- 新增 `src/workbench/imageSizes.ts`，共享档位分类、尺寸预设、去重解析与单模型尺寸数量上限。
- 预设覆盖 1:1、16:9、9:16、3:4、4:3、3:2、2:3、21:9；只追加缺少的尺寸，保留原尺寸、模型 ID、默认服务与 Key。
- 2K 示例包含 2048×2048、2560×1440、1440×2560；4K 示例包含 3840×2160、2160×3840 和约 800 万像素的 2880×2880、2496×3328 等。
- 这些是配置示例，不是供应商能力清单；用户可以继续手动编辑具体像素值。服务不一定接受每一项。
- 档位分组保留原有边长规则，增加像素量判断：长边至少 3840 或像素数至少 750 万归 4K；否则长边至少 2048 归 2K，其余归 1K。避免约 800 万像素方图/竖图被误归 2K。实际请求始终使用界面显示的具体尺寸。
- 单模型配置上限由 16 个提升为 32 个，容纳三个档位的尺寸；仍校验边长 256–4096、16 的倍数、宽高比 1:3–3:1，不放宽非法尺寸。
- 分辨率控件采用单个原生 fieldset 分组，避免重复的同名 group；窄窗与已有主题样式沿用现有 tokens。

## 验证

- `npm run build -- --emptyOutDir=false`、`npm run check:ui`、`npm run test:styles` 通过；样式错误 0，126 组对比度检查无失败。
- `npm test`：408 项通过，包含档位分类、全部预设的尺寸约束和配置容量。
- `cargo test --manifest-path src-tauri/Cargo.toml --lib generation::tests`：17 项通过；验证 4K 示例合法、超过 32 个尺寸被拒绝。`cargo build` 通过。
- `node tests/image-resolution.browser.mjs`：浅/深主题、缺失档位进入配置、原 Key/尺寸保留、追加去重、2K/4K 选择、4K 方图分组、390px 和配置不创建任务通过。
- `node tests/generation-redesign.browser.mjs`、`node tests/image-generation.browser.mjs`：原尺寸、比例、画廊、键盘/触屏、任务与配置回归通过。
- `npm run test:cdp -- --images`：真实 WebView2 → Tauri → Rust → 本地 mock，通过原生保存超过 16 个尺寸、读取包含 UHD、4K 方图/横图与 2K 选择，并继续验证文生/图生、失败页、移除/恢复与真实 pi 聊天。

CDP 使用临时 exe、WebView2 profile、生成目录、pi 配置与虚拟 Key，保留 localStorage 快照/恢复。没有读取或改写用户真实服务配置，没有发起真实 2K/4K 模型请求或验证账户权限。

截图位于 `dist/image-resolution/`，已检查窄窗配置后档位与具体尺寸；原生场景沿用 `dist/image-gallery-cdp.png`、日志 `dist/cdp-dev.log`。这些生成产物不入库。

尚未包括自动模型尺寸发现、供应商专有的 `resolution` 参数、超过 4096 边长及价格估算。当前请求仍为通用 Images 接口的 `size: WIDTHxHEIGHT`，实际支持与返回规格以服务商为准。
