# 031 · 对话页视觉与交互修改

状态：已实现，mock 浏览器双主题验证完成。创建日期：2026-10-25。实现检查与验收证据见 [verification.md](verification.md)。

来源：对话页视觉评审讨论。最终范围：第 1、2 点保持现状，修改第 3–8 点。4–8 的细化已合并进本文，编号沿用之前，可直接交给实现 AI。实现说明：Web 预览卡因当前无真实数据源暂未实现（见 verification.md），其余条目均已落地。

## 总体目标

在保留 Skiff 当前简洁、克制、留白充足的设计风格上，提升命令记录的可扫读性、助手正文的视觉层级、任务结果的承接能力，以及输入框和消息操作的主次关系。

这次是对现有对话页做增量优化，不重新设计整个页面，不照搬 Codex，不引入渐变、重阴影或过度卡片化。优先复用项目现有组件、主题变量、图标库和交互能力，样式修改尽量限定在对话页范围内。

## 明确保持不变

- 保留现有顶部“用时 + 展开箭头 + 分隔线”的折叠结构，不重新设计运行组。
- 保留“思考—执行—思考”的原始顺序，不跨阶段聚合命令。
- 保留思考标签的状态逻辑：运行时显示实时思考片段，完成后收回为普通“思考”标签。
- 不要在完成后永久展示灰色思考摘要，也不要给思考标签额外生成总结。
- 不为了界面标题增加模型请求，不伪造撤销、编辑、预览等尚未具备的功能。

## 3. 优化命令行的信息展示

折叠状态下的命令行不再直接拼接大段原始命令，而是采用：

```text
[终端图标] 动作摘要                 [状态] [展开箭头]
```

动作摘要完全通过确定性规则生成，优先级为：

1. 工具调用本身已有可靠的标题或描述时，使用该标题。
2. 能够识别主命令时，使用内置规则映射。
3. 没有映射但识别到主程序时，显示“执行 Bash · 主程序名”。
4. 无法可靠解析时，回退为“执行 Bash 命令”。

首批规则只需覆盖高频场景：

| 主命令 | 折叠行标题 |
|---|---|
| `ls` / `dir` | 查看目录内容 |
| `find` / `fd` | 查找文件 |
| `rg` / `grep` | 搜索文件内容 |
| `cat` / `head` / `tail` | 读取文件 |
| `rm` / `del` / `Remove-Item` | 删除文件或目录 |
| `git status` | 查看仓库状态 |
| `git diff` | 查看代码变更 |
| 常见测试命令 | 运行测试 |

对于 `cd ... && ls -la` 这类能够可靠识别的简单组合，可以跳过前置 `cd`，使用后面的主命令生成标题。单独执行 `cd` 时显示“切换工作目录”。复杂管道、多重命令或解析不确定时不要猜测，直接使用通用回退标题。

Shell 名称应根据实际环境显示 Bash、PowerShell 等，不要全部硬编码为 Bash。删除、覆盖、重置等高风险命令，标题中必须保留 `rm`、`git reset` 等关键操作信息，不能完全被模糊的友好文案替代。

展开命令后，展示完整原始命令、工作目录、退出状态及已有输出，并提供复制命令按钮。运行中、成功、失败应有明确但克制的状态差异；失败使用语义色和图标，不要给整行铺大面积红色背景。

## 4. 让助手正文成为视觉主角

正文、过程记录和辅助元信息需要形成明确的三级文字层级：

| 内容 | 建议样式 |
|---|---|
| 助手正文 | 16px，行高 1.7–1.75，主文本色 |
| 思考、命令和工具标签 | 13–14px，行高约 1.5，次级文本色 |
| 时间、Token 等元信息 | 12–13px，弱化但保持可读 |
| 原始命令与输出 | 12–13px，等宽字体 |

正文颜色应明显深于过程记录，避免正文、命令、思考都使用接近的灰色。次要文字可以降低对比度，但正常文字仍应满足基本可读性，不能为了“轻盈”而大量使用过浅的灰色。

Markdown 正文保持当前无气泡的阅读形态。段落间距建议为 12–16px，列表缩进控制在 20–24px，列表项间距约 6–8px，避免列表过度向右缩进。

行内文件路径和代码继续使用轻量代码样式，但背景、圆角和内边距要统一，不要显得比正文重点更突出。正文中的标题、加粗和代码块沿用统一的 Markdown 类型尺度，不在对话页里单独出现另一套字号体系。

流式输出时保持行高和容器尺寸稳定，避免文字更新造成明显布局抖动。

## 5. 增加结构化任务结果卡片

结果卡片放在助手最终正文之后、消息操作栏之前。它用于承接真实产生的文件、变更和预览结果，不是把普通回答装进卡片。

首批支持以下类型：

- 文件变更卡：展示“已创建／已编辑／已删除 + 文件名”，有数据时显示增删行数，例如 `+185 -0`。
- 多文件变更卡：多个文件优先聚合为“修改了 3 个文件”，展开后查看每个文件，避免连续堆叠多张卡。
- 删除结果卡：显示删除数量和可展开的对象清单；没有增删行数时不显示 diff 数据。
- Web 预览卡：显示预览图标、名称和“打开预览”操作。

卡片采用单行或轻微双行结构：左侧为结果图标，中间为标题和次要信息，右侧为操作按钮。建议圆角约 12px、内边距 14–16px、卡片间距 12px，使用细分隔边框和轻微背景层级，不使用厚重阴影。

文件卡可以根据现有能力提供“查看变更”“打开文件”“撤销”等操作，但只能展示真实可用的操作。没有 diff 数据就不显示增删行数，没有撤销能力就不显示撤销按钮。

卡片数据必须来自已有的工具结果或结构化事件，不要让模型根据正文猜测，也不要通过解析 Markdown 假装生成变更数据。普通问答、解释和纯文本任务不渲染结果卡片。

正文负责表达结论，卡片负责表达结构化结果。卡片已经包含完成状态时，界面组件不要再额外叠加重复的大号成功提示。

## 6. 统一内容网格和垂直节奏

以现有助手正文容器为基准，统一运行标题、工具行、正文、结果卡片、用户气泡和输入框的左右边界。用户气泡仍然右对齐，但其右缘应与整体内容网格一致，不要每个区域分别使用略有差异的宽度。

优先通过共享容器、布局变量或相同样式 token 对齐，不要针对某个截图单独写固定像素偏移。

间距统一使用现有 spacing token；如果现有体系不完整，可采用 4、8、12、16、24、32、40px 这一组尺度。建议：

- 用户消息与运行标题之间保持约 32–40px，消除无意义的大块空白。
- 运行标题分隔线与最终正文之间保持约 20–24px。
- 普通过程步骤之间保持约 8–12px，工具行高度约 36–40px。
- 最终正文与结果卡片之间保持约 20px。
- 多张结果卡片之间保持约 12px。

保留现在的整体内容宽度，不为了“高级感”随意缩窄正文，也不要把展开过程强行改成嵌套滚动区域。

用户气泡保持轻量，建议最大宽度为内容区的 70%–75%，多行文本行高约 1.6，内边距约 12px 16px，圆角约 16px。窄屏下允许提高最大宽度，避免长文本被压成狭窄竖条。

长路径、长文件名和长命令需要分别处理：卡片和折叠行可单行截断，展开详情及正文允许换行，并确保用户仍能查看完整值。

## 7. 调整输入框的视觉主次

保留现有附件、模型选择、思考模式和发送按钮的功能及大致位置，不重新设计输入流程。

当前 `medium` 等思考模式控件的强调程度不应高于发送按钮。模型和思考模式控件默认使用中性文字、图标和轻量背景；选中状态可以通过浅底、小标记或轻微边框表达，不再使用醒目的高饱和描边抢占视觉焦点。

发送按钮需要具有明确状态：

- 输入为空：使用弱化的禁用样式。
- 存在有效输入：使用实心主色背景和高对比图标，成为输入区最主要操作。
- 正在运行：如果已有停止能力，则切换为停止按钮；没有该能力时不新增假交互。
- 键盘聚焦：提供清晰可见的 focus 样式。

输入框默认边框适当减弱，聚焦时通过品牌色描边或柔和的外层 focus ring 强化，不要同时使用重边框和重阴影。

空白状态可减少无意义的纵向空白，建议最小高度约 112px；随着输入自动增长，达到既有上限后再内部滚动。占位文字保持次级层级，但不能过淡。

附件、模型选择等图标按钮应具有统一尺寸、悬停反馈、tooltip 和至少约 32px 的点击区域。窄屏下允许控件换行或收缩，不能相互覆盖或溢出。

## 8. 统一图标与消息级操作

思考、终端、文件、复制、用量、成功、失败和展开箭头等图标，统一使用项目现有图标体系，保持一致的视觉尺寸、线宽和圆角风格。常规行内图标建议为 16px 左右，状态图标可以略有区别，但不能混杂线性图标、填充图标、图片和 emoji。

由界面组件渲染的成功、失败、警告状态使用统一语义图标，不使用 ✅ 等 emoji 作为 UI 图标。不要全局过滤或替换模型正文中的 emoji，避免破坏用户内容。

助手消息底部保留复制、更多操作、Token 用量和时间，但拉开层级：复制和更多属于操作，用量和时间属于辅助元信息。操作图标可以默认弱化，在消息 hover 或 focus 时增强；元信息保持弱显示，不抢正文。

用户消息可在气泡右下方设置轻量操作行，包含时间和复制；编辑、重新发送等操作只有在现有功能支持时才展示。操作行风格与助手消息一致，不引入另一套按钮样式。

如果采用 hover 显示操作，必须预留固定空间，避免鼠标移入时页面跳动；同时保证键盘 `focus-within` 和触屏环境可用。所有纯图标按钮都需要 tooltip 和可访问名称。

## 实现约束

- 优先修改现有组件和样式，不重写整个对话页。
- 使用现有主题变量和语义色，兼容当前主题，不硬编码只适用于浅色背景的颜色。
- 不增加模型调用，不为了显示标题修改实际执行的命令。
- 不新增无后端能力的按钮，不展示伪造的统计或状态。
- 保持现有流式输出、折叠、工具展开和消息操作行为。
- 对长文本、长路径、窄屏、键盘操作和触屏操作做基本适配。

## 验收标准

1. 顶部折叠方式不变，运行时思考片段和完成后的收回逻辑不变。
2. 命令折叠行能显示确定性的动作标题，未知命令正常回退，完整命令仍可展开查看。
3. 连续多步任务中，正文明显比思考、命令和元信息更突出，没有大片低对比度文字。
4. 文件变更和 Web 预览能根据真实数据渲染卡片；普通问答不会出现多余卡片。
5. 用户消息、正文、过程区、结果卡片和输入框的左右边界一致，长内容不会撑破布局。
6. 输入框中发送按钮成为主要操作，模型和思考模式控件不再更抢眼。
7. 图标风格统一，消息操作在鼠标、键盘和触屏环境下均可使用。
8. 至少覆盖纯问答、长思考与多工具任务、命令失败、单文件修改、多文件修改、Web 预览和超长路径等场景。
